# 大脑 / 工具分离与网格 relay：方案分析

> 状态：**设计分析，未实现**
>
> 需求（用户提出）：
> - 把「工具」「大脑」分开，各自通过中枢提供功能
> - relay 做成网状：viewer 连任意 relay，都能选择不同的「大脑」和「工具组」组合
> - 工作区语义：**工具在哪台机器，就只用那台机器的目录作为工作区**

---

## 1. 现状：耦合点在哪

一个执行端进程里同时装着三样东西：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 大脑 | `providers.*` | 调 LLM，流式返回 token 与 tool_use |
| 工具 | `internal/tools` | 读写文件、执行命令、搜索等（**操作本机文件系统**） |
| 会话状态 | `driver` + `conversation` + `store` | 回合状态机、事件日志、重放 |

**关键发现：大脑与工具已经被抽象成两个方法**（`internal/host/host.go:32`）：

```go
type Runtime interface {
    OpenStream(ctx, sel providers.Selection, req providers.ChatRequest) (<-chan providers.Event, error)  // ← 大脑
    RunTools(ctx, tc *tools.ToolContext, calls []tools.Call) []tools.ToolOutcome                          // ← 工具
}
```

这是整个方案可行的**技术支点**：把这两个方法各做一套"远程实现"，就能把大脑和工具拆到别的进程/机器。

其余可复用的基础设施：

- `wire.Conn`：分帧 + 心跳 + 多路复用，已经是节点间通信的通用管道
- relay 的 `register` / `route` / `host_id`：已经是"节点注册 + 按名路由"
- `catalog.models`：大脑已经能把模型列表发布出去
- `mobile/bridge`：证明"远程调用同一套逻辑、边界只传 JSON"可行

## 2. 工作区语义（用户已定）

> 工具在 A 机器上，就使用 A 机器的目录作为工作区。

这一定义把"工具节点"明确为**自带工作区的执行器**，好处是：

- 语义清晰：工具就是"在那台机器上做事"，不存在"跨机器操作文件"的幻想
- 实现直接：远程调用 = 把 `Call` 转发过去，在那边用它的 `ToolContext` 执行
- 安全边界自然：那台机器的权限就是它的边界（`AllowShell` 也是它自己配的）

**必须明确的推论**：

- 一个回合里如果调用了两个工具节点的工具，它们操作的是**两台不同机器**的文件
- 模型需要知道"这个工具属于哪台机器"，否则会以为在改同一个工作区
- 因此工具**必须带机器/节点前缀**暴露给模型（见 §4.3）

## 3. 目标形态

```
                    ┌─────────────┐
                    │   viewer    │  任选大脑 + 任选工具组
                    └──────┬──────┘
                           │ wire
                    ┌──────┴──────┐
                    │   中枢       │  会话状态、回合编排、事件日志
                    └──┬───────┬──┘
            ┌──────────┘       └──────────┐
      ┌─────┴─────┐              ┌────────┴───────┐
      │ 大脑节点   │              │  工具节点 A/B   │
      │ (LLM API) │              │ (各自的工作区)   │
      └───────────┘              └────────────────┘
```

三种节点角色：

| 角色 | 职责 | 状态 |
| --- | --- | --- |
| **大脑节点** | 只做 LLM 调用（`OpenStream`） | 无状态（除了 API Key） |
| **工具节点** | 只做工具执行（`RunTools`）+ 自己的 `ToolContext` | 无状态（工作区在磁盘上） |
| **中枢** | 会话/回合/日志/编排 | **有状态**（这是核心） |

**关键洞察：拆出去的是"无状态能力"，留下来的是"有状态编排"。**
这让拆分比想象中简单——大脑和工具节点都可以随意重启、多副本，不需要复杂的共识协议。

## 4. 必须解决的难点

### 4.1 工具发现与描述（最大的设计工作量）

现在模型看到的工具来自本地 `tools.Builtin(allowShell)`，编译期固定。远程工具需要：

**工具清单协议**：工具节点注册时/被查询时，报告自己能干什么：

```json
{
  "node_id": "builder-pc",
  "workspace": "/home/rex/project",
  "tools": [
    {"name": "read_file", "description": "...", "schema": {...}},
    {"name": "run_command", "schema": {...}}
  ]
}
```

要点：
- `schema` 必须能直接喂给模型的 tool 定义（现在是 `ToolDef` 结构，需要能序列化）
- `workspace` 要暴露，因为它是"这台机器的工作区"（用户要能看到并选择）

**代价**：`internal/tools` 里的 `ToolDef` 需要可序列化，且 schema 要能从 JSON 还原成模型可用的定义。这块现在是编译期构造的闭包，改造要动 `registry.go`。

### 4.2 工具命名空间

两个工具节点都有 `read_file` 时必须能区分。方案：**暴露给模型的名字带节点前缀**：

```
builder-pc/read_file      ← builder-pc 这台机器上的 read_file
laptop/edit_file
```

模型返回的 `tool_use.name` 就是这个全名，中枢按前缀路由到对应节点。

**要注意**：这会让 system prompt 里的工具说明变长（每个工具都带前缀），且模型可能不擅长处理带 `/` 的名字。备选是 `builder_pc__read_file`（下划线，更保险）。

### 4.3 一个回合跨多节点的失败语义

一个回合变成：

```
大脑流式返回 tool_use(builder-pc/read_file)
  → 中枢转发给 builder-pc
  → 等结果（可能超时/节点掉线）
  → 结果喂回大脑
  → 循环
```

失败情形变多：

| 情形 | 现在 | 拆分后需要定义 |
| --- | --- | --- |
| 工具执行失败 | 返回 error 给模型 | 同 |
| 工具节点掉线 | 不存在 | **整个回合失败？还是只让这一步失败并告诉模型？** |
| 大脑节点超时 | 重连续传 | 续传的游标怎么跨节点？ |
| 中枢重启 | 从 JSONL 重放 | 重放时如何恢复"进行中的远程调用"？ |

**建议**：第一版接受"远程节点失败 = 该回合失败"，把复杂度压到最低。续传仍只在"中枢 ↔ viewer"这一跳做（那是已经跑通的）。

### 4.4 网状 relay

现在的 relay 很薄：注册 + 按 host_id 路由，**不知道回合需要几个节点协同**。

两个选择：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A. relay 保持薄** | 中枢自己去连多个 relay，组合逻辑在中枢 | 中枢要维护多个连接；但 relay 不用改 |
| **B. relay 变厚** | relay 知道节点角色，能"组合路由" | 违背"relay 只转发"的设计，改动大 |

**建议 A**：中枢已经有一个 `host.Remote` 的能力（连远端），扩展成"连多个 relay、每个 relay 上有不同角色的节点"即可，relay 一行不用改。

## 5. 分阶段演进（建议）

| 阶段 | 内容 | 改动面 | 风险 | 价值 |
| --- | --- | --- | --- | --- |
| **1** | **大脑可远程**：`OpenStream` 指向远端节点，工具仍本地 | 小（换一个实现） | 低 | 用别处的 API Key / 算力 |
| **2** | **工具可远程**：`RunTools` + 工具发现 + 命名空间 | 中（要动 tools 包的序列化） | 中 | 真正的"工具分离" |
| **3** | **多节点组合**：一个回合用 A 的大脑 + B、C 的工具 | 中大（编排与失败语义） | 中高 | 你描述的理想形态 |
| **4** | **网状 relay**：viewer 跨 relay 自由组合 | 大（路由与发现） | 高 | 完全体 |

**阶段 1 的投入产出比最高**：它验证"远程大脑"这条链路，且不碰工具语义。做完之后你会清楚知道延迟、断线、认证这些实际问题，再决定要不要继续。

---

## 6. 现在就能确定的三个设计原则

1. **中枢是唯一有状态的角色**。大脑和工具节点必须无状态、可随意重启，否则网状组合会变成分布式状态同步噩梦。

2. **工具名带节点前缀**，工作区由工具节点决定。模型看到的是 `node/tool`，用户界面上要能显示"这个工具属于哪台机器、它的工作区是什么"。

3. **第一版不做跨节点续传**。远程调用失败就让回合失败（并在事件日志里写清原因），续传只在"中枢 ↔ viewer"这一跳保留。

## 7. 待确认

1. 大脑节点与工具节点是否允许在**同一台机器**上（比如本机既当大脑又当工具）？——影响配置形态
2. 一个会话是否允许**中途换大脑/换工具组**？——影响事件日志与重放语义（现在 `selection.changed` 只记模型）
3. 认证模型：每个节点各自带 token，还是复用 relay 的 token / TLS 指纹？——现在 relay 那套能否直接复用
4. 是否接受"远程节点失败 = 回合失败"这个第一版简化
