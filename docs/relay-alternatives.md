# relay 有没有现成服务可替代？

> 状态：调研结论，**不改代码**（用户 2025-11 只问不动）

---

## 1. relay 到底在做什么

`internal/relay` 做三件事，缺一不可：

1. **执行端注册 + 心跳保活**（谁在线、叫什么名字）
2. **展示端按 `host_id` 路由**到某个执行端
3. **多路复用**：多个展示端共享同一条到执行端的物理连接
   （`executorLink.viewers` 是"逻辑通道 id → 展示端连接"的映射）

合起来是：**懂本协议的会话注册中心 + 应用层反向代理**。

## 2. 现成方案对照

| 方案 | 能替代哪部分 | 缺什么 |
| --- | --- | --- |
| frp / rathole / ntfy | 内网穿透 | 不懂本协议；没有 hostID 路由与多路复用 |
| Cloudflare Tunnel | 内网穿透 + 自带 TLS/鉴权 | 同上；且依赖外网 |
| Tailscale / Netbird / ZeroTier | **直接消除 relay 的需求** | 需要装客户端 |
| coturn（TURN） | 中继字节流 | 只是管道，没有注册/路由语义 |
| Redis / etcd | 服务发现 | 不转发 |
| MQTT broker（EMQX/Mosquitto） | 天然 topic 路由 + 认证 | 不适合流式会话与大文件，要重写协议 |
| nginx stream / K8s Service | L4 转发 | 不懂 hostID，做不了"展示端选执行端" |

**结论：没有现成服务能直接顶替。** relay 的核心价值就是"懂 `relay.register` /
`relay.route` / 通道 id 这套协议"，通用组件都不认它。

## 3. 三条务实路线（若将来想换）

### A. 不要 relay，改用虚拟网络（最省事）

用 Tailscale / Netbird / ZeroTier 让执行端与展示端在同一虚拟网内，
执行端 `--listen`，展示端 `--connect <虚拟IP>`。

- 代码改动：**0 行**
- 代价：执行端要装客户端；失去"多个执行端任选"

### B. relay 换成端口隧道（中等取舍）

用 frp / rathole / Cloudflare Tunnel 把执行端的 `7801` 暴露到公网，
展示端直连该地址：

```
展示端 --TLS--> 公网入口 --隧道--> 内网执行端(7801)
```

- 代价：一台执行端一条隧道；**失去 `relay.list`（列出所有在线执行端）**
- 收益：不用自己维护 relay

### C. 保留 relay（现状）

若"多个执行端、按名字选一个连"这个能力有价值，relay 就是必要的。

- 代码量很小（`internal/relay` 约 500 行），维护成本低
- 可托管在任何有公网 IP 的小机器（1 核 512MB 足够，只转发字节）
- 已有 `--tls` 自动证书 + 指纹校验 + token + 失败限流

## 4. 当前安全能力对照（relay 侧）

| 能力 | 状态 |
| --- | --- |
| 传输加密（TLS + 指纹） | ✅ 已实现 |
| 口令认证 | ✅ 已实现 |
| 失败限流（按 IP 指数退避） | ✅ 已实现 |
| 多凭据 / 单设备吊销 | ❌ 未做 |
| 账号系统（OIDC） | ❌ 已评估，暂不做（见 `account-evaluation.md`） |

## 5. 一句话总结

**relay 不是"标准件"，它是这个项目的私有协议中枢。** 想省掉它，正确方向不是
"找个现成 relay"，而是"换一种连接方式"（虚拟网络或端口隧道）——但那会牺牲
"多执行端可切换"这个特性。
